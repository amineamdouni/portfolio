<Section number="01" title="The problem">

At the faculty this project was designed for, final-year projects (PFE, projet de fin d'études) were managed through emails, Excel files and informal exchanges, so students lacked visibility on deadlines, progress and supervisor feedback. Nexus brings the whole process into one platform: an admin assigns subjects, supervisors follow progress, students report it, and past years stay searchable. Each role has its own access.

</Section>

<Section number="02" title="What I built">

I built Nexus as a solo project between 2025 and 2026, from a project deck that defined the actors, the use cases and three sprints, then a requirements document that added institutions, messaging, notifications and an AI module.

The core covers every use case of the first three sprints:

- Admin: create and delete students and supervisors, create, edit and delete PFE subjects, assign a PFE to a student and a supervisor, see all PFEs, and see the students of each supervisor.
- Supervisor: see the PFEs they supervise, follow their progress and move them forward.
- Student: see their own PFE, update its status and progress, and upload a PDF deliverable.
- Everyone: a dashboard with statistics for their role, a searchable archive and history (by year, supervisor and theme), a profile page, and an English and French interface with a toggle.

A PFE moves through six statuses: Proposed, Assigned, In progress, Submitted, Finished, Archived. Two rules are enforced on the server and shown in the interface: a student can have only one active PFE, and a person assigned to an active PFE cannot be deleted.

The November 2026 update added the rest of the requirements:

- Institutions and plans: each school has its own data and settings, and one of three plans (Essentiel, Standard, Étendu) that caps the PFEs created per academic year at 300, 600 or 1,200. The admin sets a report deadline.
- Supervisor profiles: expertise keywords and a capacity. A full supervisor can't take another PFE, and the list shows active projects against capacity.
- Messaging: one thread per PFE between the student and the supervisor, with unread counts. The admin can read but not write, and an archived PFE is read-only.
- Email notifications on assignment, report upload and every status change, in English and French.
- Follow-up alerts: a To watch list flags PFEs due within 7 days, late, or with no progress or upload for 14 days.
- A public landing page with a one-click demo per role, and a user guide that explains each role's tasks.

</Section>

<Section number="03" title="The AI module">

The AI suggests, and a person decides. It is on for the Standard and Étendu plans only, with a monthly budget per institution.

- **Report summaries.** When a student uploads the report or submits the PFE, a background job reads the PDF, removes names, emails, phone numbers and ID numbers, and asks Claude Haiku 5.5 for a summary of about 150 words, 5 to 8 keywords, a theme and the language. The output is checked (JSON, length, language, no grade) and retried once on Claude Sonnet 5.5 if it fails. It is labelled "Generated by AI"; the supervisor can correct it and the admin can regenerate it.
- **Supervisor suggestions.** Code first keeps up to 8 supervisors who have room and whose expertise matches the subject. Claude Sonnet 5.5 then ranks them with a score out of 100 and a two-sentence reason, from the subject, expertise and load only, never student data. If no answer arrives within 10 seconds, the list sorted by load is shown instead. One click assigns the chosen supervisor through the normal rules.
- **Cost control.** Every call is logged with its task, model, input and output tokens and cost in dollars. Once the month's spend reaches the budget the admin set, generation pauses until the next month. The settings page shows the spend and how many suggestions the admin accepted.

</Section>

<Section number="05" title="Under the hood">

A pnpm monorepo with `apps/api` (NestJS 11, Prisma 6, PostgreSQL) and `apps/web` (Next.js 16, React 19, Tailwind CSS 4, next-intl). The interface is built from a design system I followed token by token, with a light and a dark theme.

The choice I would defend: the one-active-PFE rule lives in the database as well as in the code. A partial unique index stops a student from holding two active PFEs even if two requests arrive at once. The delete rule locks the user row, so deleting someone and assigning them at the same moment cannot leave a PFE active without its person. Both have race tests.

Sign-in sets an httpOnly cookie from Next route handlers, and a proxy adds the bearer token on the way to the API, so the browser never holds it. The web proxy blocks sign-in and password paths in any letter case. Logging out revokes the token on the server.

Emails and AI jobs go through queues in Postgres rather than being sent inside the request. The email worker runs every 15 seconds, retries with a back-off and never sends a message twice. Every query is scoped to the user's institution, so a school only sees its own users, PFEs, messages and statistics.

<Section number="06" title="API and backend">

Modules cover health, auth (login, demo login, logout), the current user (profile, password), users (students, supervisors), PFEs (CRUD, assignment, status, progress, archive and restore, deliverables), messages, institution settings, AI (summaries, supervisor suggestions, usage), and stats per role. Global guards handle rate limiting per client IP, JWT (the user is loaded on every request, with a token version and a forced password change for new accounts) and roles. Errors have stable codes. The migration adds raw SQL for the partial unique index and for checks on progress (0 to 100), deliverable size (2 MB at most), ID number format and lower-case email.

Without an Anthropic API key, the AI module runs in a mock mode that returns fixed output at no cost, so the whole flow works locally.

Tests: 6 unit tests for the status transition table, 45 end-to-end API tests (both rules including a concurrent race, assignment, every role and transition returning the right 403 or 409, ownership, deliverables, revoked tokens, the temporary-password flow, and the 429 and 413 limits). CI runs lint, typecheck, unit, end-to-end and build on every push, and the API is deployed to Render only when CI passes.

</Section>

<Section number="07" title="Result">

Every requirement is covered, the AI module included, and all of it runs in the live demo.

**What I would improve.** Send real emails through an SMTP server (the demo only logs them), use batch processing to lower the cost of report summaries, add an automatic quality check of the summaries, and write end-to-end tests for the features added in November.

</Section>
