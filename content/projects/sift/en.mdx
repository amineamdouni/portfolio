<Section number="01" title="The problem">

Small teams need a place to see what is being worked on, who owns it and what is next. A board with columns and tickets is the familiar answer, but it only works if people can have different roles on different boards: some manage the board, others just move their own tickets.

</Section>

<Section number="02" title="What I built">

The first version, built in August 2025 during a Full Stack Developer internship, was a Trello-style project management app with a Java and Spring Boot backend: boards, tasks, labels and custom workflow stages, then team invitations, role-based permissions and task assignment.

Sift is the version I rebuilt as a solo project. The API keeps the original design and the call shapes, with the same `/api/dashboards` paths, and the interface is new, built from a design system I followed screen by screen.

The app has a boards home, a board with columns and tickets, drag and drop that is saved (mouse, touch and keyboard), and a ticket panel with its own URL: description, labels, assignees, dates, checklists and comments. Admins of a board manage members, labels and categories; Members work on tickets and do not see the controls they cannot use. There is a light and a dark theme, loading and error states, and an account page.

</Section>

<Section number="04" title="Under the hood">

The API is Java 21 and Spring Boot 3.5 with stateless JWT security, Spring JDBC and Flyway on PostgreSQL. The web app is React 19 with Vite, React Router, TanStack Query, Tailwind CSS 4 and dnd-kit.

The decision I would defend is how ordering works. Categories and tickets have integer positions, and one endpoint takes the new layout of a board, locks the board row, checks every id and rewrites only the changed positions in a single transaction. The unique position constraints are deferrable, so the rewrite can pass through states that would otherwise collide. The board updates optimistically in the browser and rolls back if the save fails.

The trade-off: the original ran on MySQL, and I moved to PostgreSQL with Flyway migrations instead of keeping the old schema. That was more work up front, but it made the deferrable ordering constraints possible.

<Section number="05" title="API and backend">

Every endpoint needs a token except login, the demo login and the health checks. The token holds the user id and the user is loaded on every request, so a deleted account stops working at once. Board roles live on the membership rather than the user, and each request resolves its resource to a board and checks the caller's role. People outside a board get a 404, so the API does not reveal that the board exists. Comment authors come from the token. Errors share one shape. Limits are 60 requests a minute per IP and 100 kB per request, plus caps per board on tickets, comments, labels and categories.

Tests are JUnit with Testcontainers on a real PostgreSQL: authentication (including a sweep that checks every mapped endpoint returns 401 without a token), board CRUD and scoping, and reordering (moves within and across columns, rollback on a foreign id, and concurrent reorders). The API runs in Docker with JVM flags set for a 512 MB host.

</Section>
